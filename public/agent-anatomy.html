Anatomy of an Agent

An "agent" isn't magic. It's a function that hands a model the right five things — and gets back something your code can use.

Today we're building, not perfecting. You'll tweak this all week to make it behave. The concepts matter more than the exact code — get the shape right, then tune.

① The five inputs

System promptwho it is + the rules
Contextthe grounding — schema, real vocab, retrieved docs
Model + settingswhich model, temperature, max tokens
Structured outputthe exact shape it must return
Query + historythe ask + the last few messages
→
THE AGENT
one model call
↓
a typed result
not a blob of text — a shape your code can branch on

Change any one of the five and the behavior changes. That's the whole job: pick the five well.

② Model & settings — pick the tool for the job

temperature
0 = deterministic, same answer every time. Use it for routing, SQL, extraction — anything where you want the answer, not a creative one. Crank it up only for brainstorming/writing.
model
A small/cheap model (gpt-4o-mini) is plenty for routing and SQL. Save the big model for synthesis. Don't pay for a Ferrari to fetch the mail.
max tokens
The ceiling on the reply. Too low = truncated answers; too high = wasted money on runaway output. Match it to the job.
structured output
Force a schema (zodTextFormat) so you get { useSql, useRag }, not prose you have to parse. Code can't if on a paragraph.

③ System prompts are cacheable — put the static part first

Providers cache the prefix of your prompt. Same opening tokens = cache hit = cheaper & faster. So keep anything that changes at the end.

breaks the cache 
Today is 2026-07-24 14:07.   ← changes every call
You write PostgreSQL for a
medical database...
A dynamic value up top means the prefix is never the same twice — nothing caches.
cache-friendly 
You write PostgreSQL for a
medical database...          ← static, cacheable
[schema + vocab]
---
Today is 2026-07-24.         ← dynamic, at the end
Static rules first, the changing bits last.

vague

  • No role boundary
  • No grounding — invents column names
  • No output contract — returns prose
specific 
You write ONE read-only SELECT.
Columns are camelCase, quoted.
Use ILIKE on display.
Real condition names: "Myocardial
Infarction"; "Hypertension"; ...
  • Clear job + hard rules
  • Grounded in real values (heart attack → the stored name)
  • Schema says what exists; grounding says what's in it

⑤ Why we send the last few messages

The model has no memory between calls. Each request is a blank slate — so we resend recent turns.

User:  "Tell me about Avery Mueller"
User:  "schedule him for Tuesday"   ← who is "him"?

Without the previous message, "him" is meaningless. History carries the referent. But history costs tokens — so we send the last ~5, not the whole conversation. Enough for context, not so much you pay for ancient history.

⑥ Human in the loop

When an agent is about to act on the world — book, send, charge, delete — a human approves first. The agent proposes; it doesn't execute.

User asks
→
Agent proposes
"Book Avery, Tue 2pm?"
→
✋ Human approves
→
Execute
book it for real
Discuss: what agent patterns have you seen in the wild? Where should a human gate the action — and where would that just be annoying? (Reading a chart = no gate. Booking an appointment = gate. Why?)

⑦ Few-shot prompting this week's homework

Zero-shot — just ask 
System: You write SQL.
User:   How many diabetics?
Works, but the model guesses your style.
Few-shot — show 2–3 examples first 
Q: patients with asthma
A: SELECT ... ILIKE '%Asthma%'

Q: oldest patient
A: SELECT ... ORDER BY "birthDate" ASC

Q: How many diabetics?   ← now it matches the pattern
Examples teach format & edge cases better than instructions.

Homework: add few-shot examples to your prompts, run a battery of ~10 questions before & after, and show what got better (or worse).
