PII obscuring: the emptied room

The front-office door can stay open with no login — because there's nothing sensitive left in the room to steal.

The one idea Obscuring is channel-based, not login-based. There are no users or roles. The MCP door always obscures; the chat door shows the full chart. Security comes from what each channel is allowed to emit, not from who's asking.

1Why no login?

The usual instinct is auth: log people in, give them roles, gate the data. But the front office doesn't need the chart — it needs to book appointments and answer "is this a real patient?" So instead of guarding a room full of secrets, we empty the room: the MCP channel only exposes non-identifying tools, and it scrubs every response on the way out. An open door to an empty room is safe.

2The real question: HOW do you de-identify?

"Scrub the PII" sounds like one step. It isn't — there are four approaches, strongest signal first:

ApproachHow it worksTrade-off
Known identifiersYou already hold the patient's name / DOB / MRN in the record → scrub those exact valuesHighest precision — you're not guessing. The anchor.
Regex / patternsMatch SSNs, phones, emails, dates by shapeFast, deterministic, auditable — but misses novel formats by design
Statistical NERA trained model tags names/places in free text by contextCatches "the patient's mother, Jane" — costs compute, still imperfect
LLMAsk GPT/Claude to rewrite the note with PII removedFlexible — but ships the PHI to a third party, non-deterministic, unauditable
The takeaway Real systems layer these — they don't pick one. Anchor on the identifiers you already know (deterministic), add NER + regex for the rest, human review for high-stakes. De-identification is defense-in-depth, and the strongest layer is the structured data you already hold.

3Why "just ask GPT/Claude" is the tempting wrong answer

  • You'd ship the PHI to the exact third party you're protecting it from. Sending the note to an external LLM to strip PHI means it already left your boundary.
  • Non-deterministic + unauditable. The same note scrubs differently run-to-run — you can't prove HIPAA Safe-Harbor compliance with "the model usually catches it."
  • The legitimate ML version is a local / self-hosted model. The issue isn't "ML" — it's "external general-purpose API."

Neither OpenAI nor Anthropic ships a dedicated de-identification API — you'd just be prompting the base model. Both offer a HIPAA BAA + zero-retention, but that's governance (lets you legally route PHI), not redaction.

4The production tool: Microsoft Presidio

When a real team needs de-identification, they reach for a purpose-built, validated tool — not a chat model.

Microsoft Presidio Open-source and self-hostable (runs on your infra — no PHI leaves), combines NER + regex + rules, oriented to HIPAA's 18 identifiers, and lets you register custom recognizers. It's the batteries-included version of what we build by hand.

Managed cloud equivalents, if you don't want to run it yourself: AWS Comprehend Medical (DetectPHI), Azure AI Language — PII detection (healthcare mode), Google Cloud Healthcare API de-identification. Clinical-specific: Philter, NLM-Scrubber, John Snow Labs.

5Where the PII lives here — the leak to hunt

Each result has two parts: metadata (structured firstName/lastName — the known identifier, obscure it directly) and content (the free-text note body, where the name also appears, plus SSNs/phones — needs a regex sweep). The lesson Regex de-identification is a mitigation, not a guarantee — it misses novel formats by design. Knowing where it fails is the job. (Our dataset is fully synthetic — zero real PHI, so hunting leaks on screen is safe.)
