Week 4 · Walkthrough

MCP: exposing your RAG as a tool

Let a model you don't control — Claude Desktop — discover and call your one medical-RAG tool, through a door that always obscures PII.

The one idea Channels. Which door a request comes through decides what it may see. The MCP door is the front-office channel — it always obscures. The chat door is clinician-facing — it shows the full chart. No login, no roles. The channel is the permission.

1What MCP actually is

MCP (Model Context Protocol) lets an outside model list and invoke your tools. You expose a small server over stdin/stdout that speaks JSON-RPC; a client (Claude Desktop, or the Inspector) launches it as a subprocess, asks it tools/list, and — when it decides a tool helps — calls it. The tool-calling loop lives in the client. Your job is just to expose a good tool and answer honestly.

In this repo the server is mcp-server/index.ts, and it exposes a single tool: query_notes — semantic search over the clinical notes, with names obscured on the way out.

2Anatomy of the tool

A tool is four things and a return shape:

name — what the model calls (query_notes)
description — when to use it; the model reads this to decide
inputSchema — a Zod object; becomes the JSON schema the model fills in
handler — your code: run the search, obscure PII, return text
returns { content: [{ type: 'text', text }] }
server.registerTool(
  'query_notes',
  {
    description: 'Search clinical notes using semantic search...',
    inputSchema: {
      query: z.string().describe('Semantic search query'),
      patientId: z.string().optional(),
      topK: z.number().optional().default(5),
    },
  },
  async ({ query, patientId, topK }) => {
    const results = await searchClinicalNotes(query, { topK, patientIds: patientId ? [patientId] : undefined });
    return { content: [{ type: 'text', text: formatVectorResults(results) }] };
  }
);
Note The text you return is rendered as markdown by the client — headings, tables, lists all work.

3Where the PII actually lives (and leaks)

Each search hit has two parts, and they obscure differently:

metadata — structured fields: firstName, lastName, etc. The name is known → obscure it directly with obscureName() (hash pseudonym: Patient-A7B3).
content — the free-text note body. The patient's name is also in here ("Carmen presented with…") plus SSNs, phones → this needs a regex sweep (obscureContent()).
The leak to hunt Obscuring only the metadata name (the header) is not enough — the note body still says the name in plain text. The front-office door must scrub the content, not just the label. That's the whole Week 4 lesson: regex de-identification is a mitigation, not a guarantee, and it misses novel formats by design.

The strong pattern (your metadata + regex idea): pull the authoritative name from metadata, build a targeted regex to scrub that exact name everywhere in the content, then run obscureContent() for the generic PII (SSN, phone, email) that isn't in metadata. Anchoring the regex on the known name closes the biggest gap that blind pattern-matching leaves open.

See the companion PII walkthrough — the obscuring itself (lib/pii.ts) is the lab: 33 tests, 31 red until you implement it.

4Run it locally — the Inspector

The MCP Inspector is a local web UI that lists and calls your tool. No Claude Desktop, no account. Raw ts-node doesn't read .env, so load your keys into the shell first:

set -a; . ./.env; set +a
npx @modelcontextprotocol/inspector npx ts-node mcp-server/index.ts

First run downloads the inspector, then opens a browser page:

  1. Connect (top-left) — the server starts, handshake completes.
  2. Tools tab → List Tools → query_notes appears.
  3. Fill in a query (e.g. chest pain) → Run → inspect the result. (Needs lib/pii.ts implemented, since the handler calls obscureName.)
Quick smoke test (no UI) To just prove it boots: echo '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}' | npx ts-node mcp-server/index.ts → a JSON-RPC tool listing, plus Medical RAG MCP server running on stderr (stdout is reserved for protocol traffic).

5Wire it into Claude Desktop

Edit ~/Library/Application Support/Claude/claude_desktop_config.json (macOS):

{
  "mcpServers": {
    "medical-rag": {
      "command": "npx",
      "args": ["ts-node", "/ABSOLUTE/PATH/to/parsity_medical_rag/mcp-server/index.ts"],
      "env": {
        "DATABASE_URL": "postgresql://...",
        "OPENAI_API_KEY": "sk-...",
        "OPENAI_BASE_URL": "https://<your-litellm-proxy>",
        "PINECONE_API_KEY": "..."
      }
    }
  }
}
The #1 gotcha The subprocess inherits no environment — every key must be in this env block, even though they're already in .env (Claude launches from an arbitrary directory). If you use a LiteLLM/OpenAI proxy, OPENAI_BASE_URL must be here too, or embeddings hit api.openai.com and your proxy key is rejected as "not right."
  • Use an absolute path to index.ts.
  • The file must be valid JSON — one stray brace and Claude silently drops all servers.
  • Fully quit Claude (Cmd-Q) and reopen after any edit — closing the window is not a restart; the config is read only at launch.
  • Tail the log to see it start (or fail): 
    tail -f ~/Library/Logs/Claude/mcp-server-medical-rag.log

6Demo it

  1. New chat → query_notes appears in the 🔌 menu.
  2. "Search the clinical notes for patients with breathing problems." → Claude calls the tool; results come back with names obscured. The front-office door working.
  3. Contrast: the same search in the app's chat UI returns the full chart. Same data, different channel, different exposure.
  4. Now hunt a leak — find PII in a note body that slipped through the regex. That's the point of the lesson.
